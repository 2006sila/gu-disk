# 参考软件功能对照清单

对照对象：五款参考软件（CrystalDiskInfo 9.6.0 / CrystalDiskMark 8.0.1 / HDTune 6.0.0.5 / SMART Doctor 1.0.0 / DiskGenius Pro 6.0.1）。
**本文档对应 Gu-disk 0.2.6。**

**0.2.6 · 机械盘真机修复（首次接上 2 块 WDC WD20EURS + JMicron JMS578 双盘位盒）**

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 两块盘都读到 `/dev/sdd` | 序列号相同时映射表互相覆盖 | 改为「索引对应 + 序列号验证」 |
| 2 | `-d` 类型错成 `usbjmicron` | PID `0xA901` 未收录兜底到错类型；且 `usbjmicron` 裸用报 "No device connected" | 补 PID → `sat`；JMicron USB-SATA 一律优先 `sat` |
| 3 | **DiskKey 冲突** | 桥给的序列号都是假值 `000000000203` | 枚举阶段对可疑 USB 盘补真身份（`DiskKey.LooksFakeSerial`） |
| 4 | 转速永远读不到 | `rotation_rate` 完全没解析 | 已解析并回填 IdentityInfo |
| 5 | 介质判定退化成「未收录」 | 过度依赖转速；IntelliPower 盘不报转速 | 改用机械盘独有属性（起转用时/寻道错误率/磁头归位） |
| 5b | **潜在误判**：「无转速」被当作 SSD 证据 | 逻辑缺陷，西数机械盘带 F1/F2 会误判 SSD | 排除机械盘特征后才认 SSD |
| 6 | CLI 属性名英文 | `smart` 命令绕过特征库 | 套用同一套特征库 |
| 7 | **属性表缺 当前值/最差/临界** | 字段已解析但从未显示 | GUI 与 CLI 均补齐（NVMe 无此体系 → 显示 `-`） |

**与 CrystalDiskInfo 9.7.2 的实测对照**：型号 / 固件 / 序列号 / 容量 / 通电时间 / 18 个属性原始值**逐个一致**；
补三列后 18 行逐列对齐。传输模式 `SATA/600` **已补**（`smartctl --identify` 的 word 76，bit1/2/3 = Gen1/2/3；
USB-SATA 桥不透过 `-i` 报 SATA Version，只能这样读；代价 +约 300ms/盘，仅对 USB-SATA 桥接盘触发）；
判定策略（CDI 只看 SMART 阈值判「良好」，
本项目把通电时长纳入「注意」）。

**0.2.5 补一条**：桌面温度悬浮窗的温度**也**要在原生引擎失败时兜底走 smartctl ——
悬浮窗与主界面是**两套独立的温度读取**，0.2.4 只给主界面加了兜底，悬浮窗漏了，
结果 USB 盘在悬浮窗上依旧显示 "--"。教训：**改变一个共享数据源的供给方式时，
要把所有消费方列出来逐个过**（主诊断 ✓ / 主界面温度 ✓ / 悬浮窗 ✗ → 已补 / 温度历史走完整诊断 ✓）。

**0.2.4 · USB 硬盘盒真机修复**（首次接上真实硬盘盒 RTL9210B + KIOXIA NVMe，发现并修掉 4 处）：

| # | 问题 | 修复 |
|---|---|---|
| 1 | 设备解析**只靠序列号匹配** —— Windows 报的是桥接芯片的序列号，smartctl 穿桥读的是盘自己的，两者天生不同，匹配永远不会命中，命令里出现 `<scan>` 占位符 | `--scan` 行里的 `-d` 类型**保留下来**并参与匹配；同类型设备恰好唯一时直接采用 |
| 2 | 对 USB-NVMe 桥接盘**发 ATA 直通**（Win32 87 = ERROR_INVALID_FUNCTION，白白等 3 ms） | 桥接类型为 snt*/nvme 的 USB 盘**跳过原生引擎**，直接由 smartctl 走厂商私有协议 |
| 3 | smartctl 读到的**盘体真身份被丢弃**，界面/历史/DiskKey 全挂在桥上（换盒子同一块盘变成"另一块盘"） | smartctl 成功后回填 Model/Serial/Firmware，并同步进盘列表 |
| 4 | 桌面温度悬浮窗显示 `--` —— 温度这条路**只走原生引擎**，被跳过后温度永远读不到 | 原生失败时兜底走 smartctl（约 280 ms，10 秒一次的刷新完全可接受） |

真机验证（RTL9210B-CG + KIOXIA EXCERIA PLUS G3 1TB）：桥接识别 ✅ / 设备解析 ✅ / SMART 全表 ✅ /
界面身份 KIOXIA + 真实序列号 ✅ / 悬浮窗温度 27.9 ℃ ✅。**USB 硬盘盒这条此前零验证的路径，现在真机通过。**

**0.2.3 相比 0.2.2 修掉的真 bug**（全在错误日志解析这条路，由"两个引擎对同一字段取法不一致"暴露）：

| # | Bug | 影响 |
|---|---|---|
| 1 | ATA 错误日志**条目基址**用了 `i*90`，应为 `2 + i*90`（前 2 字节是日志头） | 整体偏 2 字节 |
| 2 | ATA **错误码**取 `[0]`（Error 寄存器），应为 `[2-3]`（扩展错误码） | 报出的不是错误码 |
| 3 | ATA **LBA** 取 4 字节 `[3..6]`，应为 3 字节 `[5..7]` | LBA 是垃圾值，且把 Device 寄存器混进高位 |
| 4 | NVMe **Uncorrectable** 取"错误计数高字节"的 bit0，应为 Status Field 的 SCT==2 | 该标志一直无意义 |

两个解析器已抽成**纯函数**并加了单测（`ata.errorlog-layout` / `nvme.errorlog-layout`）—— 本机没有 SATA 盘，
**测试是这条路径唯一的守卫**。测试里特意把旧算法也算一遍，确认它给出不同结果，避免"测不出回归的假测试"。

同时清掉 3 个编译器警告（CS0675 符号扩展 / CS0649 死字段 / CS9336 冗余条件）与 1 个确认无引用的死类。

状态图例：**✅ 已有** · **⚠️ 部分** · **❌ 没有** · **🚫 明确不做**

> 主线结论：**"读数据 → 给出可信判定"这条线，我们已经比参照做得多**
> （双引擎逐字段交叉校验、四档状态判定带逐条依据、DiskSpd 对标过的测速、失败回退定位的坏道扫描）。
> 剩下的差距都是**外围能力**，集中在硬件覆盖面和"跑分"类功能。

## 六、还剩什么

### 6.0 联网调研后的增补（0.2.1）

调研对象：HDDScan / StableBit Scanner / GSmartControl / Hard Disk Sentinel 官方功能页，
以及 Backblaze 的 SMART 统计博客、Google FAST'07《Failure Trends in a Large Disk Drive Population》。

**P0 · 已解析但从未使用过的字段（全部在真盘上验证过）**

| 补了什么 | 判定行为 |
|---|---|
| NVMe 温度累计时间（警告/临界） | **参与判定**：越过临界温度 → 注意 |
| NVMe 温控降频次数与时长 | **只展示不判级** —— NVMe 规范没规定多少次算多，拿到真实基线再定阈值 |
| NVMe 多传感器 | 概览温度副行"N 个传感器 · 最高 X ℃"；S.M.A.R.T. 页逐条列出 |
| 主机读/写命令数 + 平均写入大小 | 概览新增两行（实测 145.1 KB/命令） |
| ATA 0xBC 命令超时 / 0xB8 端到端 / 0xBD 高飞写入 | 三条新谓词 |
| ATA 0xC0 断电磁头归位 | **只展示** —— 每次正常断电都会计数，判成异常就是纯噪音 |
| ATA 0xBE 气流温度 | 作为 0xC2 的兜底温度源 |

**顺带修掉的两个真 bug**：
① 概览对 NVMe **硬编码"支持 TRIM"** —— 实际 TRIM 在 NVMe 里叫 Dataset Management，挂在 Identify Controller `0x100` 的 ONCS bit 2，现已真解析；
② 双引擎交叉校验的温度容差原为 **±1 K**，两次读取之间隔着一个 smartctl 进程（约 200 ms），实测 40 ℃ / 38 ℃ 就报"1 项不一致" —— 现放宽到 **±3 K**。

**P1 · 三条基于"变化"而非"状态"的规则**

| 项 | 依据 | 落地 |
|---|---|---|
| **变化速率** | Backblaze：绝对值一样、变化速率不同 = 不同的盘 | 历史记录 0x05/0xC5/0xC6/0xC7；30 天内增长 → 警告，带"从 X 涨到 Y" |
| **首次不可纠正错误后的 60 天窗口** | Google FAST'07 | 首次出现 0xC6 起 60 天内出警告（措辞写成"统计相关性，不是必然"） |
| **扫描结果跨次对比** | **参考软件里没见谁做好** | 每盘存最近一次快照（坏块/慢块偏移分开存），结论后追加"与上次相比：新增坏块 N 个" |

**必须同时记住的一句（来自 Google 论文）**：

> 很大比例的故障盘在四个强警告上**没有任何计数** —— 多数故障事前毫无征兆。

这句话界定了任何基于 SMART 的工具的能力边界，应出现在报告页的说明里。

### 6.1 A 档已全部完成（2026-10-13）

| 项 | 落地方式 |
|---|---|

**RAID 那件的边界（说清楚，别当成全做了）**：

## 七、附：我们的独有项（参照软件都没有）

| 项 | 说明 |
|---|---|
| **逐字段交叉校验** | 原生引擎与 smartctl 各读一遍，15 项逐字段比对，不一致会明确标出来 |
| **四档状态 + 逐条判定依据** | 不给 0–100 分（用户明确要求）。每条结论都能指回一个真实 SMART 字段：来源 → 原始值 → 判读 → 建议，正常项也列进「已核对项」 |
| **使用习惯指标降级处理** | 不安全关机这类不判"危急"，最高只到"注意"（≥1000 才警告），不跟介质缺陷同级惊悚 |
| **热力图按每块耗时分七档** | 耗时对机械/固态是同一把尺子；按吞吐量分档会让固态永远"优秀"、机械永远"差" |
| **降采样到固定格数** | 扫 1 GB 是 1024 格，扫 4 TB 也还是 ≤1536 格 —— 否则 WPF 会被 400 万个控件卡死 |
| **温度独立刷新** | 与整体诊断解耦：温度只走原生引擎（约 20 ms），可以 5 秒刷一次 |
| **按时间跑测速 + 混合读写** | CDM 的 TestMix 与 Measure Time 的对应实现 |
